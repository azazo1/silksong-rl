# Boss 强化学习训练设计

这套东西由两部分组成:

- `mods/rl-env`: 游戏内插件, 负责观测采集, 动作注入, 回合编排与通信.
- `trainer/`: Python 侧, 负责环境封装, 奖励计算与 PPO 训练.

两者用本机 TCP 上的一条长度前缀二进制协议通信, 奖励与算法完全在 Python 侧, 因此调整训练
不需要重编插件, 调整采集内容才需要.

## 数据流

```
Python 训练进程                         游戏进程 (RLEnv 插件)
  reset()  ──── Reset 命令 ───────────►  载入 Boss 存档 → 同场景重载 → 等就绪
           ◄─── Observation (episode_start) ──
  act(a)   ──── Step 命令 (4 个 int32) ─►  覆写 HeroActions → 放开 N 个物理帧
           ◄─── Observation (值 + 终止标志) ───
  ...                                      ...
  终止后回到 reset()                       等下一个 Reset
```

## 观测

字段表由 `mods/rl-env/src/Observation/ObservationSchema.cs` 唯一定义, 连接时通过 `Hello`
消息发给 Python, 训练侧按名字取值. 当前 216 个字段, 分四段:

| 段 | 内容 |
| --- | --- |
| 主角 (40) | 场地归一化坐标与世界坐标, 速度, 朝向, 自身碰撞箱半宽半高, 血量与上限, 灵丝与上限, 是否落地/起跳/二段跳/下落/冲刺/贴墙/滑墙/看上看下/攻击/上劈/下劈/蓄力/受击/无敌/缚丝/死亡/危险死亡/场景切换, 是否接受输入, `hero_state` |
| Boss (18) | 存活, 相对主角的归一化位移, 速度, 朝向, 血量与比例与上限, 全体本体血量比例, 距离, 动作阶段 id, 是否无敌, 世界坐标, 碰撞箱半宽半高 |
| 场地 (4) | 场地中心与半宽半高, 回合开始时抓一次, 回合内固定 |
| 时间与事件 (8) | 物理帧号, 回合 step 序号, 本步造成伤害, 本步受到伤害, Boss 击杀, 主角阵亡, 场上小怪数, 附近危险框数 |
| 最近 6 个小怪 (66) | 每只: 是否有效, 相对主角的归一化位移, 速度, 血量与比例, 碰撞箱半宽半高, 朝向, 敌人类型 |
| 最近 8 个危险框 (72) | 每个: 是否有效, 相对主角的归一化位移, 碰撞箱半宽半高, 距离, 伤害值, 危险类型, 是否激活 |
| Boss 各 FSM (8) | 最多 4 个 PlayMakerFSM 的当前状态 id (另有全部 FSM 拼成的总 id 在 Boss 段) |

设计取舍:

- 坐标归一化用回合开始时固定的场地矩形, 不用实时相机视野, 否则相机会跟着主角动, 观测非平稳.
- 小怪与危险框都按"离主角最近"排序截断, 并给出 `*_count` 表示实际数量, 超出名额的信息不丢总量.
- 危险框来自场景里所有 `DamageHero` (敌人攻击判定, 陷阱, 掉落物, 投射物), 未激活的也会上报
  (`enabled=0`), 让智能体提前看到"这边有攻击判定体".
- Boss 的动作阶段同时给两种粒度: 全部 FSM 状态拼成的总 id, 以及按 FSM 名排序的前 4 个状态 id,
  映射表通过 `StateMap` 消息增量同步. 这些 id 是每个会话重新分配的, 不能直接当特征用, 要按
  状态名重映射成跨会话稳定的编号, 做法见 `trainer/README.md` 的"观测"一节.
- 原始值 (世界坐标, 速度, 血量) 一并发送, Python 侧用 `VecNormalize` 归一化, 便于改观测尺度.

## 动作

`MultiDiscrete([3, 3, 2, 2, 2])` = `[左右, 上下, 跳跃, 攻击, 缚丝]`. 一个 step 内按键保持按住,
与真人握手柄一致; 想让跳跃/攻击这类边沿动作再次触发, 必须让下一步把按键松开. 这样跳跃的
可变高度 (松手把上升速度砍半) 与蓄力这类按住语义都保持原样.

攻击方向由"上下"与主角朝向共同决定 (上劈 / 前劈 / 下劈), 与游戏输入层一致; 主角朝向由左右
输入改变, 所以"朝哪边打"是左右加攻击的组合, 不需要单独的方向维度.

"缚丝"对应游戏的 `Cast` 键, 满丝时按住可以回 3 点血, 是长局里唯一的回复手段.

## 步进时序

1. Python 发 Step, 插件在当前物理帧末采样随机状态之前先把动作写入虚拟输入面板;
2. 时间倍率从 `IdleTimeScale` 提到 `Speed`, 让世界开始推进;
3. 计数 `StepFrames` 个物理帧 (采样点挂在 `CustomPlayerLoop` 的 super-late fixed update,
   保证伤害与死亡已经结算);
4. 到点或出现终止事件, 就把时间倍率压回 `IdleTimeScale`, 采样观测并发给 Python.

不用 `Time.timeScale = 0` 做暂停: 那会让 `FixedUpdate` 与游戏协程整体停摆, 场景载入这类
协程会永久挂起. 改用极小非零倍率 (`IdleTimeScale`), 世界几乎不动但仍然是活的.

训练期间还会屏蔽 `GameManager.FreezeMoment` 顿帧, 否则受击/击杀插进来的顿帧会把
"一个 step 等于固定帧数" 这个前提打乱.

## 回合重置

只有重载场景能让被销毁的 Boss, 弹幕与场地物件回到初始状态, 因此重置原语就是"换一份干净的
存档数据 + 发起一次同场景重载". 具体步骤与坑见 `mods/rl-env/README.md` 的"工作方式"一节,
其中最关键的是重置窗口内必须屏蔽 `GameManager.SaveLevelState()`, 否则旧场景的持久化项会把
新数据写脏, 表现为新场景里 Boss 隐形且战斗不触发.

以苔藓之母 (场景 `Tut_03`) 为例, 一回合的完整流程与实测耗时:

| 阶段 | 做了什么 | 首次 | 后续回合 |
| --- | --- | --- | --- |
| 破门 | 主角被摆到 `Moss Vine Cluster` 门前, 反复挥针打烂两个藤蔓门 | 约 6 秒 (4 倍速下) | 跳过 |
| 缓存 | 把"门已破"这一刻的 `SceneData` 存成 JSON | - | - |
| 重载 | `SetLoadedGameData` + `ReadyForRespawn` 重载同场景 | 约 3 秒 | 约 3 秒 |
| 进场 | 主角摆进竞技场 (触发框不可用时退化为站到 Boss 身前) | - | - |
| 唤醒 | 给 Boss 发 `WAKE` 事件 | - | - |
| 就绪 | 等 Boss 的 FSM 状态签名变化 + 空转几帧 | - | - |
| 合计 | | **约 11 秒** | **约 4.4 秒** |

几个只有实测才能发现的关键点:

- **门口的两个藤蔓门不是 `Breakable`**: 它们挂着 `PersistentBoolItem + PlayMakerFSM +
  PlayMakerTriggerEnter2D + ReceivedDamageProxy`, 破门逻辑写在 FSM 里. 与其去猜 FSM 事件名,
  不如让主角真的走过去用针打烂, 走游戏自己的判定链路. 是否破掉用持久化项 `Moss Vine Cluster`
  是否翻成 true 判断 (不能用"FSM 状态变了"判断, 打第一下就会换状态, 门其实还在).
- **Boss 在 `Dormant` 状态等的是 `WAKE` 事件**, 不是 `BATTLE START`:
  `Control` FSM 的 `Dormant` 状态里有 `WAKE->Start Battle` 这条转移, 触发条件与"主角是否在场地内"
  有关. 所以顺序必须是"先破门 → 再进场地 → 再发 WAKE".
- **主角死亡不能等游戏自己的死亡流程**: 原版是 `GameManager.PlayerDead` 协程里等 4 秒, 写盘,
  预载场景, 然后复活切场景; 这套流程和我们的重置会同时发起场景切换, 结果卡在载入界面.
  现在训练期间直接用 Harmony prefix 把 `PlayerDead` / `PlayerDeadFromHazard` 整个跳过,
  主角就地躺下, 由随后的场景重载恢复.
- **等 Python 决策时不能把时间倍率设成 0**, 否则游戏自己的协程全部停摆; 用 `IdleTimeScale`
  (默认 0.0005) 让世界几乎不动但仍然活着.
- **"本步事件"必须在每个记录步结束时清零**: 训练路径每步都会 `CombatTracker.BeginStep()`,
  录制路径一开始漏了这一句, 于是示范里的 `damage_dealt_step` 变成整局的累计值 (0 一路涨到
  Boss 总血量), 与训练时同一列的每步增量完全不是一个东西. 现在录制路径也按步清零, 录制脚本
  与行为克隆两侧都会检查这一列是不是单调不减, 发现是累计值就清零并告警.
- **抓游戏画面不能用外部抓屏工具**: Windows 的 gdigrab 抓的是屏幕上的那块区域, 游戏窗口只要
  不是最前面那个, 抓到的就是盖在它上面的窗口 (实测抓到过一整段静止的文档窗口). 回合回放因此
  由插件自己用 `ScreenCapture` 抓后备缓冲, 被遮挡也能抓.

## 回合回放

插件在训练期间按固定频率把画面编码成 JPEG 放在内存环形缓冲里 (只保留最近若干秒), 一局结束时
训练侧发 `SaveClip` 告诉它这局是不是击杀: 是就把缓冲写成图片序列, 训练侧用 ffmpeg 合成
`runs/<实验名>/kills/kill-NNN-*.mp4` 并删掉原始帧; 不是就清掉. 这样长时间跑不会堆垃圾, 也不需要
人盯着按下录制键.

## 推荐流程: 先示范, 再强化

从零开始的随机探索打不赢 Boss (苔藓之母 120 血, 主角只有 5 血), 所以流程是"先模仿人, 再自我提升":

1. `uv run silksong-record --episodes 5 --out records/moss-mother`
   插件把 Boss 房准备好后交给你操作, 期间把 (观测, 你的真实按键) 成对流给 Python 落盘,
   同时把这一局的 Boss 状态编号映射存成 `state-map-*.json`.
2. `uv run silksong-bc --data records/moss-mother`
   行为克隆出一个 stable-baselines3 PPO 模型 (`runs/bc/bc.zip`), 并在旁边写下状态词表.
3. `uv run silksong-train --resume runs/bc/bc.zip --finetune --timesteps 200000 --speed 6`
   在这个起点上做 PPO 微调 (`--finetune` 给的是保守超参, 漏掉它会把模仿出来的策略冲掉).

示范数据与训练用的是同一套观测字段, 同一套动作分档, 同一个步长, 因此可以直接监督训练.

实测: 起点是 12 局人类示范 (3097 条样本), 克隆后在验证集上单维准确率约 0.93, 但直接放回游戏
闭环里只能撑 79-135 步, 每回合造成 5-10 点伤害 —— 模仿的闭环漂移很典型. PPO 微调把这个数
抬到 300 步上下, 每回合 25 点左右, 然后进入平台期.

## 长时间训练

采样速度由游戏实时帧率决定, 实测约 20 步/秒 (训练期把分辨率降到 640x360 之后), 也就是一小时
七万步左右, 而 PPO 要的步数是百万量级, 所以按"分段接力"跑:

```shell
just chain 5 100000
```

每段结束从这一段的 `final.zip` 接着练下一段, 每段开始前确认游戏进程还在, 掉线就请求
`tools/game-control.ps1` 把它拉起来. 逐回合日志落在 `trainer/runs/<段名>/episodes.jsonl`,
随时可以用 `just report runs/<段名>` 看分段趋势.

## 奖励

奖励在 `trainer/src/silksong_rl/reward.py` 里算, 输入是相邻两帧观测. 默认项:

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 造成伤害 | +1.0 / 点 | 来自插件对 `HealthManager.Hit` 的 hp 前后差, 已过游戏自身的伤害缩放 |
| 受到伤害 | -1.0 / 次 | 订阅 `HeroController.OnTakenDamage`, 只在确认扣血时触发 |
| 击杀 Boss | +25 | |
| 自己阵亡 | -25 | `OnDeath` 与 `OnHazardDeath` 都订阅 |
| 每步 | -0.002 | 鼓励速战 |
| 接近 Boss | 0 (可选) | 按归一化距离的减少量给奖励, 势函数形式, 不改变最优策略 |
| 贴身 | 0 (可选) | 每步停在攻击距离内就给的密集奖励, 实测对伤害没有帮助, 默认关 |

回合结束时除了回报与伤害, 还会记几个诊断量到 `episodes.jsonl`: `attack_pressed_steps` (按下攻击
的步数), `close_steps` (进入攻击距离的步数), `damage_per_press` (每按一次的收获). 实测这套数
据把"打不动"定位成了"够不着 + 出手时机不对": 策略按下攻击的频率 (29%) 比人 (21.7%) 还高,
但进入攻击距离的步数只占 7% (人约 21%), 于是每按一次只换来 0.2 点伤害 (人 1.77).

## 尚未验证的点

代码是按反编译结论写的, 但下面这些必须在游戏里实测确认. 前七项已经验过 (结果见上文的
耗时表与"只有实测才能发现的关键点"): 打完 Boss 后重置能正常开打, 重置后场景名等于目标场景,
`SceneData` 不再被写脏, 每回合耗时已分解, 观测与画面自洽, 长跑后重置耗时与进程占用不涨.
还剩下的:

1. 5 号槽位与真实存档 0-4 的隔离: 训练前后比对 `user0..4.dat` 的哈希 (会动真实存档, 需要先确认).

连续重置的实测数据: 一次实验跑满 277 个回合, 重置耗时按四分位切开是首段 4.09 s / 末段 4.05 s
(最大 4.61 s), 没有随回合数变慢; 同期的游戏进程私有内存约 2.2 GB, 句柄数 1009, 与开跑前一致,
场景对象也没有缺失 (缺失时 `ReadyForRespawn` 不会就绪, 会直接超时).
